# Meal Planner data and the Drive mailbox

How Claude (or anything else) reads Meal Planner's data and sends changes back. The phone is the source of truth;
Drive is a mailbox between the phone and Claude.

```
meal-planner-data/            (Google Drive, next to the meal-planner repo folder, never inside it)
  inbox/    Claude writes patch files here  → the app shows them, Brad taps Apply
  outbox/   the app writes latest.json here → Claude reads it
```

The two folder IDs are in `meal-planner-data/README.md` in Drive, not in this repo.

Naming: the **Larder** on screen is the `pantryItems` store in the data. The data name predates the rename and is kept
so older exports, the tablet and patches keep working.

## Reading: the outbox

- `outbox/latest.json` is a full export of everything on the phone, overwritten about a minute after any change
  (and when the app goes to the background). It's only as fresh as the last time the app was open and signed in to Google:
  check `exportedAt`.
- `outbox/meal-planner-YYYY-MM-DD.json` holds one snapshot per day; the last 14 days are kept.
- Only the phone (the app's "Main phone" device) writes the outbox. View-only devices (kitchen tablet, PC) just read latest.json.

A full export looks like this:

```json
{
  "app": "meal-planner",
  "schemaVersion": 1,
  "appVersion": "1.1.0",
  "exportedAt": "2026-10-08T07:12:01.000Z",
  "stores": {
    "ingredients": [], "recipes": [], "weekPlans": [], "shoppingItems": [],
    "pantryItems": [], "mealLogs": [], "settings": []
  }
}
```

Every record has `id` (UUID), `createdAt` and `updatedAt` (ISO 8601, UTC).

| Store | Fields | Notes |
|---|---|---|
| ingredients | `name`, `defaultUnit`, `store`, `aisle`, `isLocal`, `lastPrice`, optional `packQty`, `packUnit`, `packPrice`, `location` | Shared by recipes. `store` is one of `settings.stores`. With a pack size (`packQty` + `packUnit`, e.g. `1` + `kg`) the shopping list buys whole packs, priced at `packPrice` (AUD per pack); without one, `lastPrice` is the line price. `location` is where it's kept in the Larder (one of `settings.locations`). |
| recipes | `name`, `servings`, `proteinPerServingG`, `lactose` (`none` / `low` / `contains`), `tags[]`, `method`, `ingredients[{ingredientId, qty, unit}]`, optional `isShake` | `qty` is for the whole recipe (all servings). Tags in use: `batch`, `quick`, `cook once eat twice`, `rice cooker`, `Costco ready-meal`. `isShake: true` marks the one-tap post-workout shake. |
| weekPlans | `weekStart` (Monday, `YYYY-MM-DD`), `days[7]` of `{date, training, slots}` | A template has `templateName` set and `weekStart: null` (and `date: null` on each day). |
| shoppingItems | `weekStart`, `ingredientId` or `text`, `qty`, `unit`, `store`, `aisle`, `checked`, `price`, `isLocal`, `manual`, `forRecipes`, optional `packs`, `buyQty`, `buyUnit`, `boughtQty`, `boughtUnit`, `needGross`, `larderQty`, `pantryAdded` | Regenerated by the app from the plan; don't write these. `qty` is what's still needed after the Larder (`needGross` before it, `larderQty` covered by it). `packs` × pack size = `buyQty`/`buyUnit`; `boughtQty`/`boughtUnit` only when a different amount was bought. `pantryAdded` = what ticking put in the Larder. `price` = what the line cost. |
| pantryItems | Ingredient stock: `ingredientId`, `qty`, `unit`, optional `location`. Prepared meals: `recipeId`, `qty` (portions), `unit: "portion"`, `location`, `cookedOn` | **The Larder** (named pantryItems in the data; "Larder" on screen). Ingredient rows go up when a bought line is ticked and down when a meal using them is cooked; `qty` 0 = run out. Prepared-meal rows are cooked portions (one row per recipe, location and cook date), added when a cook is confirmed and taken when that recipe is eaten (fridge first, oldest first); a row eaten down to 0 is removed. |
| mealLogs | `date`, `slot`, `recipeId` or `text`, `servings`, `proteinG`, `planned`, `extra` | What was actually eaten. `planned: true` = eaten as planned; `false` with `extra: false` = swapped; `extra: true` = eaten in addition. Optional `skipped: true` (with `text: "Skipped"`, `proteinG: 0`) = the planned meal wasn't eaten. Optional `pantryUsed: [{ingredientId, qty, unit}]` = what cooking took from the Larder (put back if the log is removed). Optional `portionsUsed: [{recipeId, qty, location, cookedOn}]` = portions eaten from the Larder; `cookedSlot: true` = this log came with cooking the batch (Undo also undoes the cook). |
| settings | one record, `id: "settings"`: `bodyweightKg`, `proteinTargetGPerKg`, `reminderTimes {evening, batchCook}`, `stores[]`, `locations[]` | Daily protein target = bodyweightKg × proteinTargetGPerKg. `locations` are the Larder's places, in display order. |

**Days and slots.** `day.training` uses Lift Log's session types: `lift`, `walk`, `hiit` or `rest`, so it joins Lift Log's data by date.
`day.slots` has up to four keys (`breakfast`, `lunch`, `dinner`, `snack`); a missing key is an empty slot. A slot is one of:

| Slot | Meaning |
|---|---|
| `{"recipeId": "…", "servings": 1, "cook": 4}` | Eat `servings` of a recipe; cook `cook` servings (null = the whole recipe). The shopping list buys for `cook`, less what Larder portions cover. |
| `{"leftoverOf": {"day": 0, "slot": "dinner"}, "servings": 1, "freezer": false}` | Leftovers of an earlier slot in the same week. `day` 0 = Monday … 6 = Sunday. `freezer: true` adds a night-before "move it to the fridge" reminder. |
| `{"text": "Eating out", "proteinG": 40}` | Free text with an optional protein estimate. |

A recipe slot that has been cooked carries `cooked: {on, made, pantryUsed, portionsAdded}`: the date, portions made, the
ingredients taken from the Larder and the portions put away. Keep it unchanged when rewriting a week; it's what stops the
list buying that cook's ingredients again. Copies of a week and templates never carry it.

**Portions cover meals first.** For each recipe, portions in the Larder (not already needed by earlier weeks) cover that week's
meals of it before anything is cooked. Recipes tagged `batch` then cook their full batch if anything is uncovered (the spare goes
in the freezer); other recipes cook only what isn't covered. Prepared meals in latest.json are worth planning around.

Units are metric: `g`, `kg`, `ml`, `L`, or a count (`each`, `tin`, `pack`, `bunch`, `loaf`). g/kg and ml/L are summed together on the shopping list.

## Writing: patch files in the inbox

Write **only the records you changed**, as a patch. Anything logged on the phone in the meantime is kept.

```json
{
  "app": "meal-planner",
  "schemaVersion": 1,
  "kind": "patch",
  "patchId": "6f1c2a9e-3b7d-4c55-9a51-0d2e8f4b7c10",
  "createdAt": "2026-10-08T09:30:00Z",
  "author": "claude",
  "note": "Plan for week of Mon 12 Oct; protein for Costco meals",
  "upserts": {
    "recipes": [ { "id": "…", "createdAt": "…", "updatedAt": "2026-10-08T09:30:00Z", "name": "…", "...": "every field" } ],
    "weekPlans": [ { "id": "…", "weekStart": "2026-10-12", "days": [ "…7 days…" ], "createdAt": "…", "updatedAt": "2026-10-08T09:30:00Z" } ]
  },
  "deletes": { "ingredients": ["id-to-delete"] }
}
```

Rules:

1. **Start from the latest `outbox/latest.json`.** Copy the record you're changing and edit the copy.
2. **An upsert replaces the whole record.** Always send every field, not just the changed ones.
3. **Set `updatedAt` to the current time** on every record you send. The app takes a record only if it's new,
   or if its `updatedAt` is later than the phone's copy. A record with an old timestamp is silently ignored.
4. **New records need a new UUID** in `id`, plus `createdAt` and `updatedAt`. New ingredients go in `upserts.ingredients`,
   and recipes refer to them by that id. Reuse an existing ingredient (match by name) rather than creating a duplicate.
5. **A new week** is a `weekPlans` record with a new id, `weekStart` set to the Monday, and exactly 7 days,
   each with `date` set. If that week already has a plan in latest.json, update that record (same id) instead.
6. **`patchId` must be unique** (a new UUID per file). The app applies each patchId once; re-sending the same patchId does nothing.
7. **Deletes** list ids per store and remove only those records. You can't delete settings.
8. Don't write `shoppingItems` (the app regenerates them) or `mealLogs` (that's Brad's record of what he ate),
   unless he asks you to correct one.
   **Larder amounts** (`pantryItems.qty`, including prepared-meal portions) change constantly on the phone as things are bought,
   cooked and eaten; only change them when Brad asks. Pack sizes, pack prices and locations on ingredients are fine to set or correct at any time.
9. Name the file `patch-YYYY-MM-DD-short-description.json`; one change set per file. Keep it under 5 MB.
   The app never deletes inbox files; old ones can be tidied by hand.

The app checks every file before showing it: `app` must be `meal-planner`, `schemaVersion` must be `1`, store names must be
the seven above, every record needs an `id` (and `updatedAt` in a patch), and required fields must be present
(for example a recipe needs `name` and `ingredients`, and a week plan needs exactly 7 days). A file that fails is shown
with the reason and can only be skipped, so fix it and write a new file with a new `patchId`.

A full export (no `kind`) in the inbox is also accepted. It's treated as upserts under the same rule and never deletes anything.

**Quick adds apply on their own.** A patch whose only change is `upserts.shoppingItems` with hand-added items
(`manual: true`, `text` set, no `ingredientId`) and no deletes is applied automatically at the next inbox check,
with a toast ("Added to shopping list: Kitty litter"). Use `weekStart` = this week's Monday and give the item every field:
`weekStart`, `ingredientId: null`, `text`, `qty`, `unit`, `store`, `aisle`, `checked: false`, `price`, `isLocal`, `manual: true`, `forRecipes: ""`.
This is the one exception to rule 8.

**Recipe and plan patches apply on their own too (since 1.6.0).** Any patch with no `deletes` that doesn't touch `mealLogs`
is applied automatically at the next inbox check, and the app shows its `note` in a toast ("Updated from Claude: …").
So write a short, clear `note`: it's what Brad sees. Rule 3 still decides what actually changes.

**Still Brad's choice:** patches with deletes, patches that change `mealLogs`, and full exports. The app shows each file's `note`
and a summary ("1 recipe updated, 1 week plan new") with Apply and Skip.
